# Замечания и архитектурный аудит проекта EduJacksons

Этот документ содержит наблюдения, выявленные в ходе анализа кода и документации. Замечания разделены по категориям: от критических архитектурных рисков до общих рекомендаций.

## ✅ Решенные проблемы

### 1. Циклическая зависимость модулей (`courses` $\leftrightarrow$ `groups`)
**Статус**: Решено (см. ADR 0005).
**Что сделано**: Интерфейс `CourseAccessQuery` перенесен из модуля `groups` в модуль `courses`. 
**Результат**: Граф зависимостей пакетов стал ацикличным (DAG): `groups` $\to$ `courses` $\to$ `auth`. Модуль `courses` больше не зависит от `groups`.

## 🛠 Технический долг (Medium)

### 1. Отсутствие механизма Refresh-токенов
**Проблема**: В текущей реализации используется только один Access-токен.
- **Риск**: Если установить короткий срок жизни токена (для безопасности), пользователь будет вынужден логиниться каждые 15-30 минут. Если установить длинный срок — возрастает риск компрометации токена.
- **Рекомендация**: Реализовать пару `AccessToken` + `RefreshToken` (хранение refresh-токена в БД или Redis с привязкой к устройству), как это заявлено в `api-contracts.md` (на данный момент реализовано только в черновике).

### 2. Покрытие интеграционными тестами межмодульных потоков
**Проблема**: В проекте есть тесты, но основное внимание уделено Unit-тестам.
- **Риск**: Ошибки в «стыковке» модулей (например, при проверке доступа к курсу через группу) могут быть обнаружены только на этапе ручного тестирования.
- **Рекомендация**: Добавить сквозные (E2E) интеграционные тесты с использованием `Testcontainers`, которые проверяют полный путь: `Request` $\to$ `CourseController` $\to$ `CourseService` $\to$ `CourseAccessQueryImpl` $\to$ `DB`.

### 3. Надежность конвейера проверки (Phase 2)
**Проблема**: Порядок «сохранение в БД $\to$ отправка в Kafka» подвержен сбоям (Ghost Submissions).
- **Риск**: Если приложение упадет после `save()`, но до `kafkaTemplate.send()`, решение останется в статусе `QUEUED` навсегда.
- **Рекомендация**: Внедрить паттерн **Transactional Outbox** для гарантированной доставки событий.

**Проблема**: Синхронное ожидание ответа от Judge0 в потоке Kafka-слушателя.
- **Риск**: При высокой нагрузке все потоки потребителя будут заблокированы в ожидании HTTP-ответов от Judge0, что приведет к лагу очереди.
- **Рекомендация**: Перейти на асинхронный API Judge0 (submit $\to$ poll/webhook).

**Проблема**: Отсутствие механизма реконсиляции «зависших» решений.
- **Риск**: Потеря сообщения в Kafka или сбой в `JudgeResultListener` оставляют решение в статусе `QUEUED`.
- **Рекомендация**: Добавить Scheduled-задачу для поиска и обработки зависших решений.

## 💡 Общие рекомендации (Low)

### 1. Типизация кодов ошибок
**Проблема**: Коды ошибок в `api-contracts.md` описаны строками (`forbidden`, `course_not_found`).
- **Рекомендация**: Создать централизованный Enum для кодов ошибок в модуле `common`. Это позволит избежать опечаток в строках и упростит поддержку фронтенда (фронт будет работать с фиксированным списком кодов).

### 2. Оптимизация транзакций на чтение
**Проблема**: Некоторые методы чтения используют стандартный `@Transactional`.
- **Рекомендация**: Повсеместно использовать `@Transactional(readOnly = true)` для методов, которые не изменяют данные. Это дает подсказку Hibernate для оптимизации (например, отключение dirty checking) и может улучшить производительность БД.

## ✅ Сильные стороны проекта
- **Строгая слоистая архитектура**: Разделение на `api / service / repository / domain` соблюдается безукоризненно.
- **Границы модулей**: Использование интерфейсов-директорий (`UserDirectory`, `CourseDirectory`) для общения между модулями — очень зрелое решение.
- **Подход к БД**: Использование Flyway и `ddl-auto=validate` исключает риск расхождения схемы БД на разных окружениях.
- **Безопасность**: Правильный выбор BCrypt для паролей и stateless-подход с JWT.
