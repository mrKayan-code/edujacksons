# 0004 — Границы модулей: публичные интерфейсы + view-записи, без цикла бинов

- **Статус:** принято (пункт 1 уточнён в ADR `0005` — 2026-07-10)
- **Дата:** 2026-07-08

> **Обновление (ADR `0005`, 2026-07-10):** интерфейс `CourseAccessQuery` переехал из `groups`
> в `courses` (порт у потребителя). Ниже по тексту он ещё указан как `groups.CourseAccessQuery` —
> это исходное решение; актуальное размещение и обоснование см. в ADR `0005`.
- **Контекст:** Фаза 1 добавила модули `courses` и `groups`, которым нужны данные друг друга и
  из `auth`: `groups` при добавлении ученика ищет пользователя по email; при назначении курса —
  проверяет, что курс существует и принадлежит учителю; `courses` при чтении учеником — проверяет,
  выдан ли курс ученику через группу. Встал вопрос, **как** модули общаются, не превращаясь в
  «большой ком грязи», раз цель проекта — модульный монолит, готовый к распилу на микросервисы.

## Проблема

Два соблазна, каждый ломает будущий распил:
1. **Лезть в чужие таблицы** (join `group_courses` ↔ `courses`, чтение `users` из `groups`).
   При выносе модуля в сервис такие join'ы через границу процесса исчезают — переписывать много.
2. **Возвращать наружу JPA-сущности** (`User`, `Course`). Тогда чужой модуль завязывается на
   внутреннюю модель и её ленивую загрузку; граница дырявая.

Плюс техническая ловушка: если модуль A зависит от интерфейса B, а B — от интерфейса A, и **оба
интерфейса реализованы «толстыми» сервисами**, получаем **циклическую зависимость бинов** —
Spring Boot по умолчанию отказывается стартовать.

## Решение

1. **Только публичные интерфейсы + view-записи между модулями.** Никаких чужих таблиц и никакой
   утечки сущностей:
   - `auth.UserDirectory` → `UserView(id, email, role, displayName)`
   - `courses.CourseDirectory` → `boolean isOwnedBy(courseId, ownerId)`
   - `groups.CourseAccessQuery` → `accessibleCourseIds(studentId)`, `canAccess(studentId, courseId)`
2. **Каждый интерфейс реализует тонкий бин-адаптер над репозиторием**, а не прикладной сервис:
   `UserDirectoryImpl`, `CourseDirectoryImpl`, `CourseAccessQueryImpl`. Адаптеры зависят только
   от своих репозиториев, поэтому граф бинов **ацикличен**, хотя модули ссылаются на интерфейсы
   друг друга. Стартуем без `spring.main.allow-circular-references`.
3. **Ссылки между модулями — по id, без FK** (`owner_id`, `student_id`, `course_id`). FK — только
   внутри модуля. Это и есть будущая граница сервиса: за ней — вызов API/события, а не join.

## Последствия

- (+) Границы честные: вынести `judge`/`ege` в сервис = заменить реализацию интерфейса на
  HTTP/Kafka-клиент, прикладной код не трогаем.
- (+) Нет цикла бинов; зависимости читаются как DAG (адаптеры — листья графа).
- (−) Больше «церемонии»: на каждое межмодульное чтение — интерфейс + view + адаптер.
  Осознанная цена за разъёмные границы (учебная цель проекта).
- Целостность межмодульных ссылок (нет FK) держим на уровне приложения: проверяем существование
  через `*Directory` перед записью (напр. `CourseDirectory.isOwnedBy` при назначении курса).
