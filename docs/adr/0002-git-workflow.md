# 0002 — Git-процесс: GitHub Flow с защитой main

- **Статус:** принято
- **Дата:** 2026-07-04
- **Контекст:** проект вёлся соло, планируется работа вдвоём с тиммейтом.

## Проблема

Прошлый опыт команды: «начинали за здравие с ветками — заканчивали тем, что всё сливалось
прямо в `main`». Нужен процесс, который (а) поддерживает параллельную работу двоих по
модулям и (б) **физически не даёт** обойти ревью/CI, оставаясь достаточно лёгким, чтобы его
не хотелось обходить.

## Решение

**GitHub Flow** + защита ветки `main`:

- `main` всегда зелёный; изменения — только через короткоживущие ветки и PR.
- **Squash-merge** — чистая линейная история, один коммит на фичу, легко откатывать.
- **Self-merge разрешён при зелёном CI** — чтобы недоступность одного не блокировала
  другого. Но:
- **Прямой push в `main` запрещён всегда** — самомёрдж идёт только через PR.
- **CODEOWNERS** требует апрув владельца, когда PR лезет в чужой модуль или в общие файлы
  (сборка, CI, схема БД, миграции) — точечная защита реального источника конфликтов.

Детали процесса — в `CONTRIBUTING.md`.

## Почему так, а не иначе

- **Почему не GitFlow** (`develop`/`release/*`/`hotfix/*`): для двоих на greenfield-монолите
  это лишняя тяжесть, которая сама провоцирует «забить и слить в main». GitHub Flow проще.
- **Почему self-merge, а не обязательный апрув на каждый PR:** команда из двоих; жёсткое
  «всегда 1 approval» блокирует, когда второй недоступен. Риск компенсируем CODEOWNERS
  (апрув нужен только на межмодульные/общие правки) + обязательным зелёным CI.
- **Почему squash, а не merge/rebase:** маленькие PR + линейная история важнее сохранения
  промежуточных «wip»-коммитов ветки.

## Последствия

- Дисциплина в своём модуле — на CI и здравом смысле; главный риск (общий код) закрыт
  жёстко. Если начнёт «протекать» — ужесточаем до обязательного апрува.
- Часть правил защиты включается только после появления CI (Фаза 0).
