# 0006 — Конвейер проверки: CodeExecutor + самодостаточное Kafka-событие

- **Статус:** принято
- **Дата:** 2026-07-10
- **Контекст:** Фаза 2 добавляет автопроверку решений. Нужно (1) исполнять код в песочнице,
  (2) сделать это асинхронно и «микросервис-готово» — `judge` первым выносится в отдельный
  сервис (`task.md` §5). Встали три вопроса: чем исполнять код, где живёт логика вердикта и
  что именно передавать судье.

## Решения

### 1. Judge0 за интерфейсом `CodeExecutor`, который только запускает код
`CodeExecutor.execute(ExecutionRequest) → ExecutionResult` **не сверяет вывод** — лишь запускает
код на одном stdin и возвращает stdout + статус процесса (OK/TLE/RE/CE/INTERNAL) и метрики.
Сверку ожидаемого вывода и агрегацию вердикта делает `JudgeService`.

- (+) Логика вердикта (нормализация вывода, приоритет вердиктов, счёт) тестируется юнит-тестом
  с fake-исполнителем — без Judge0 и Docker (см. `JudgeServiceTest`).
- (+) Бэкенд исполнения заменяем (Judge0 → свой sandbox позже) без переписывания логики проверки.
- Реализация на старте — `Judge0CodeExecutor` (HTTP, `wait=true`, один сабмит Judge0 на тест,
  Python `language_id=71`). Judge0 self-hosted — опциональный профиль `judge0` в docker-compose.
- В тестах `CodeExecutor` подменяется `@Primary` fake-бином; реальный клиент в тестах не вызывается.

### 2. Асинхронность через Kafka, событие проверки — самодостаточное
Поток: `submissions` сохраняет решение (`QUEUED`) и шлёт `JudgeRequest` в топик `judge.requests` →
`judge` исполняет и шлёт `JudgeResult` в `judge.results` → `submissions` слушает и проставляет
вердикт + по-тестовые результаты.

`JudgeRequest` **несёт всё**, что нужно судье: код, язык, лимиты и полный набор тестов. Судья
не обращается к таблицам/портам других модулей — только исполняет заявку.

- (+) Максимально «разъёмная» граница: при выносе `judge-service` меняется лишь транспорт
  (Kafka-топик ↔ сетевой вызов), а не логика — ровно цель из ADR `0004`.
- (+) `judge` не зависит от `problems`/`submissions` на уровне пакетов (только от `common` +
  собственного контракта `judge.api`). Граф модулей — DAG: `submissions → {problems, judge}`,
  `problems → courses → auth`.
- (−) Тестовые данные едут в сообщении. Для Python/ЕГЭ-задач это мелочь; если наборы вырастут —
  переключимся на «судья тянет тесты по id» (появится порт `judge → problems`, при выносе — HTTP).
- Контракт (`JudgeRequest`/`JudgeResult`/`Verdict`/`JudgeTopics`) живёт в `judge.api` — это
  публичный API будущего сервиса. `submissions` его импортирует (producer + consumer результата).

### 3. Публикуем заявку после коммита строки решения
`submissions.save()` коммитит в своей транзакции, и только потом публикуется `JudgeRequest`.
Иначе быстрый судья успевает вернуть результат раньше, чем строка `submissions` видна слушателю
результата, — и итог проверки теряется.

- (−) Если публикация упадёт после коммита, решение останется `QUEUED` (перепроверку добавим позже
  — ретраи/outbox). Осознанная простота для MVP.

## Модель статусов и вердиктов
- `SubmissionStatus`: `QUEUED` → `FINISHED` (проверено, вердикт выставлен) / `FAILED` (`INTERNAL_ERROR`).
- `Verdict` (общий и по тесту): `ACCEPTED`, `WRONG_ANSWER`, `TIME_LIMIT_EXCEEDED`, `RUNTIME_ERROR`,
  `COMPILE_ERROR`, `INTERNAL_ERROR`. Общий = `ACCEPTED`, если все тесты прошли; иначе вердикт
  первого непройденного. `score`/`total_tests` — прошедшие/всего.
- Сверка вывода: хвостовые пробелы в строках и лишние переводы строк в конце игнорируются;
  пробелы внутри строки значимы.

## Сериализация Kafka
Значения — JSON (`JsonSerializer`/`JsonDeserializer`), тип берётся из заголовка `__TypeId__`,
trusted packages `dev.edujacksons.*`. Один consumer-factory обслуживает оба топика; группы —
`judge` и `submissions`. Топики создаёт `KafkaAdmin` из `NewTopic`-бинов (1 партиция для MVP).
