# Модуль Groups (`groups`)

Модуль отвечает за организацию учеников в группы и назначение этим группам конкретных курсов. 
Фактически, этот модуль управляет правами доступа студентов к учебным материалам.

## 🎯 Назначение
- Создание и управление группами преподавателем.
- Управление составом группы (добавление/удаление учеников).
- Назначение курсов группе (связывание контента с аудиторией).
- Предоставление данных о доступе к курсам для модуля `courses`.

## 🏗 Архитектура модуля

Модуль следует стандартному многослойному подходу:
- `api/`: Контроллеры (`GroupController`) и DTO.
- `service/`: Бизнес-логика. `GroupService` — основной API модуля.
- `repository/`: Доступ к таблицам `groups`, `group_members` и `group_courses`.
- `domain/`: Сущности `Group`, `GroupMember` и `GroupCourse`.

### Ключевые компоненты

| Компонент | Ответственность |
|---|---|
| `GroupService` | Управление жизненным циклом групп, проверка ролей при добавлении участников, валидация владения курсом при назначении. |
| `CourseAccessQueryImpl` | Реализация интерфейса из модуля `courses`. Позволяет проверить, имеет ли студент доступ к курсу через любую из своих групп. |

## 🔐 Бизнес-правила и ограничения

В модуле реализованы следующие критические проверки:

1. **Владение группой**: Все операции с группой (изменение состава, назначение курсов) доступны только её создателю-преподавателю.
2. **Валидация роли**: В группу можно добавить только пользователя с ролью `STUDENT`. Попытка добавить другого пользователя вызывает `NotAStudentException`.
3. **Связь с курсами**: Преподаватель может назначить группе только тот курс, который принадлежит ему самому. Это гарантирует, что учитель не сможет дать доступ к чужому контенту.
4. **Идемпотентность**: Повторное добавление одного и того же ученика в группу или одного и того же курса в группу не приводит к дублированию записей в БД.

## 🔄 Интеграция и борьба с циклическими зависимостями

Одной из главных архитектурных задач было взаимодействие между модулями `courses` и `groups`. 
- Модулю `courses` нужно знать, может ли ученик видеть курс (зависит от групп).
- Модулю `groups` нужно знать, существует ли курс и принадлежит ли он учителю (зависит от курсов).

**Решение**:
В модуле `courses` определен интерфейс `CourseAccessQuery`. Модуль `groups` реализует этот интерфейс в классе `CourseAccessQueryImpl`. 
Поскольку `CourseAccessQueryImpl` зависит только от репозитория `GroupCourseRepository` и не вызывает `CourseService`, граф зависимостей остается ацикличным:
`courses` $\to$ `CourseAccessQuery` $\to$ `groups` (реализация).

## 🚀 API Эндпоинты

### Группы
| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/groups` | Teacher | Создание группы |
| `GET` | `/api/groups` | Teacher | Список своих групп |
| `GET` | `/api/groups/{id}` | Owner | Детали группы (участники + курсы) |

### Участники
| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/groups/{id}/members` | Owner | Добавление ученика по email |
| `DELETE` | `/api/groups/{id}/members/{sid}` | Owner | Удаление ученика из группы |

### Курсы
| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/groups/{id}/courses` | Owner | Привязка курса к группе |
| `DELETE` | `/api/groups/{id}/courses/{cid}` | Owner | Отвязка курса от группы |

## 🛠 Технические детали
- **Связи**: Используются промежуточные сущности `GroupMember` и `GroupCourse` для реализации отношений Many-to-Many.
- **Поиск**: Поиск ученика при добавлении в группу осуществляется через `UserDirectory` (модуль `auth`).
