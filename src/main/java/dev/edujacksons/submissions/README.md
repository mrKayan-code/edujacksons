# Модуль Submissions (`submissions`)

Модуль отвечает за прием решений задач от учеников, отслеживание их статусов и хранение итоговых результатов проверки.

## 🎯 Назначение
- Прием исходного кода решения от ученика.
- Валидация языка программирования и прав доступа к задаче.
- Инициация процесса асинхронной проверки через Kafka.
- Хранение истории всех попыток решения.
- Предоставление результатов проверки (вердикты по каждому тесту и общий итог).

## 🏗 Архитектура модуля

Модуль следует стандартному многослойному подходу:
- `api/`: Контроллеры (`SubmissionController`) и DTO.
- `service/`: Бизнес-логика. `SubmissionService` управляет жизненным циклом решения.
- `repository/`: Доступ к таблицам `submissions` и `submission_results`.
- `domain/`: Сущности `Submission` (попытка) и `SubmissionResult` (результат конкретного теста).

### Ключевые компоненты

| Компонент | Ответственность |
|---|---|
| `SubmissionService` | Валидация, сохранение попытки, публикация запроса в Kafka, обновление статуса по результату. |
| `JudgeResultListener` | Kafka-слушатель, который принимает вердикты от модуля `judge` и записывает их в базу данных. |
| `SubmissionStatus` | Перечисление состояний: `QUEUED` (в очереди), `FINISHED` (проверено), `FAILED` (ошибка системы). |

## 🔄 Конвейер обработки решения (Pipeline)

1. **Прием**: Ученик отправляет код $\to$ `SubmissionController` $\to$ `SubmissionService`.
2. **Валидация**: Проверяется доступ к задаче и поддержка выбранного языка.
3. **Персистенция**: Создается запись в БД со статусом `QUEUED`.
4. **Публикация**: В топик `judge.requests` отправляется самодостаточное событие `JudgeRequest` (код + все тесты задачи).
5. **Ожидание**: Решение находится в статусе `QUEUED`, пока Judge0 его исполняет.
6. **Завершение**: `JudgeResultListener` ловит ответ из Kafka $\to$ обновляет статус на `FINISHED` $\to$ записывает результаты по каждому тесту в `SubmissionResult`.

## 🚀 API Эндпоинты

| Метод | Путь | Доступ | Описание |
|---|---|---|---|
| `POST` | `/api/submissions` | Student | Отправка решения задачи |
| `GET` | `/api/submissions/{id}` | Owner/Student | Текущий статус и детальный результат проверки |
| `GET` | `/api/submissions/my` | Student | История всех своих попыток |

## 🛠 Особенности реализации
- **Асинхронность**: API не ждет завершения проверки (которая может занять секунды). Вместо этого возвращается ID решения, а фронтенд опрашивает (polling) статус по нему.
- **Гарантии**: Публикация в Kafka происходит строго после коммита транзакции в БД, чтобы избежать ситуации, когда судья вернул результат быстрее, чем запись о решении появилась в базе.
- **Изоляция**: Модуль не знает, как работает Judge0. Он общается с ним через строго определенные контракты событий в Kafka.
